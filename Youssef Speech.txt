#kafka
Dans notre projet, Kafka est la couche centrale de streaming. 
Le producer lit les reviews du fichier test_reviews.jsonl, 
les envoie sous forme de messages JSON dans le topic amazon_reviews, 
qui est divisé en 6 partitions et répliqué sur 3 brokers. 
Spark Structured Streaming consomme ensuite ces messages depuis Kafka.

#spark streaming
Dans la partie Spark Structured Streaming,
D’abord, l’application crée une SparkSession. 
Ensuite, elle charge le modèle de machine learning sauvegardé, sous forme de PipelineModel. 
Dans notre cas, le modèle utilisé en streaming est one_vs_rest_linear_svc.

Après cela, Spark se connecte au topic Kafka amazon_reviews et commence à lire les messages comme un flux continu. 
Les messages Kafka arrivent avec plusieurs colonnes techniques, 
comme le topic, la partition, l’offset et surtout la colonne value. 
Cette colonne value contient le message JSON sous forme binaire. 
Spark convertit cette valeur de bytes vers string.

Une fois le message converti en texte, Spark parse le JSON pour obtenir des colonnes structurées :
product_id, user_id, score, summary, text, label et review_date. 
Ensuite, il prépare la colonne text, car c’est cette colonne qui est attendue par le pipeline de prédiction.

Quand les données sont prêtes, Spark applique le modèle avec model.transform(). 
Cette étape ajoute une prédiction numérique, par exemple 0.0, 1.0 ou 2.0. 
Spark la convertit ensuite en label compréhensible : positive, negative ou neutral.

Après la prédiction, Spark enrichit chaque résultat avec des métadonnées comme 
batch_id, processed_at, source et model_type. 
Ces informations permettent de savoir dans quel micro-batch la review a été traitée, 
à quel moment, et avec quel modèle.
En parallèle, il sauvegarde aussi sa progression dans un checkpoint, notamment les offsets Kafka déjà traités. 
Grâce à ce checkpoint, si Spark s’arrête ou tombe en panne, 
il peut redémarrer et reprendre le traitement à partir du dernier offset sauvegardé, 
au lieu de recommencer depuis le début.

Enfin, Spark écrit chaque micro-batch dans MongoDB.
